# Daily Proposal Research — 2026-09-14

Project: 3D Scene Understanding with 2D Vision-Language Models via Abstract 3D Representations and Viewpoint Alignment

## Fresh scan result
No newly surfaced paper from 2026-09-13/14 was strong enough to replace the current shortlist. The important update today is a novelty-boundary correction after re-checking GraFT and the current object-selection baselines.

## Important correction: GraFT is a stronger near-task baseline than previously ranked
**GraFT: A Training-Free Framework for Spatial Reasoning in Multimodal Large Language Models via 3D Scene Graphs** (arXiv:2609.03892, 2026-09-03) is directly relevant to the core proposal, not merely a generic scene-graph baseline. It is training-free and reports direct ScanQA gains. Its 3DSG exposes three capabilities: deterministic symbolic geometry, allocentric BEV rendering, and visual-attribute grounding via task-relevant egocentric frames. Therefore, a contribution framed only as `3D scene graph + geometry + task-relevant view/render selection` is now too weak.

### Novelty implication
The object-selection contribution must be stricter:
`question -> seed hypotheses -> relation/question-type constraints -> global candidate generation -> QA-support evidence allocation -> selected object subset -> PoseAlign-T -> selective Abstract3D render`

The claim must be **object/subscene evidence retention before rendering**, under a matched object/render budget, with explicit preservation of unnamed supporting objects. GraFT should be treated as a strong near-task baseline / novelty limiter for training-free ScanQA reasoning.

## Candidate refinement: QASER-CF (Constraint-First QA Evidence Retention)
### Research Hypothesis
For ScanQA/SQA3D, selecting a small object subset using question-conditioned relation constraints before rendering can preserve QA evidence better than (a) semantic Top-K, (b) local KNN/radius, and (c) scene-graph reasoning that still relies on broader scene context/rendering.

### Stage changed
Question-conditioned object/subscene selection before PoseAlign-T and Abstract3D rendering.

### Object-selection rule
1. Hard-retain seed objects explicitly or referentially grounded from the question.
2. Parse question/relation type.
3. Generate candidates over the appropriate global object set; do not impose generic KNN/radius or semantic Top-K as an early hard gate.
4. Use relation-specific geometry only where the relation warrants it (adjacency for `next to`, containment for `inside`, directional coordinates after PoseAlign-T for left/right/front/behind, etc.).
5. Allocate a fixed object budget K among surviving support candidates using relation compatibility plus optional semantic/diversity tie-breakers.

### Supporting-context rule
Supporting objects may be unnamed in the question. Keep them when they satisfy a relation path, serve as disambiguating anchors, or preserve the local/global configuration needed by the question. Distance is a feature only for relations that imply distance; it is not a universal gate.

### Expected benefit
- Lower clutter in Abstract3D renders.
- Lower object/render budget while retaining answer evidence.
- Better robustness than semantic-first retrieval when the answer/support category is absent from the query.
- Better robustness than KNN when valid evidence is distant or global.

### Difficulty / compute
Implementation difficulty: medium. Geometry and graph operations are CPU-light; GPU cost remains dominated by the <=7B 2D VLM. No selector training is required for the initial version. Estimated additional VRAM for selector: negligible; practical VLM VRAM depends on quantization/backbone but no larger backbone is required.

### Data / metrics
Primary: ScanQA, SQA3D.
QA metrics: dataset-standard answer metrics plus same-backbone comparison.
Selection metrics/proxies:
- Object Reduction Ratio (ORR)
- Question Entity Coverage (QEC)
- Supporting-Context Retention (SCR; proxy/derived labels if no direct GT)
- Context-loss rate
- QA accuracy/CIDEr/EM versus object budget K
- average rendered objects per query

### Required ablation
`Full scene` vs `GraFT-style near-task baseline` vs `semantic Top-K` vs `Seed+KNN` vs `Seed+radius` vs `CAPruner endpoints` vs `PruneGround-style anchor expansion` vs `Constraint-first global candidates` vs `Constraint-first + support-budget allocation` vs `+PoseAlign-T`.
All selective methods must be compared at matched object budget when possible.

### Risk
Main risk: ScanQA/SQA3D lack direct GT for every supporting object, so SCR may need counterfactual/ablation-derived proxy labels. Another risk is query parsing error; the first implementation should keep fallback candidate expansion rather than aggressive pruning.

### Publication potential
Moderate if only implemented as deterministic rules; stronger if the work demonstrates a consistent QA-vs-object-budget Pareto improvement across ScanQA and SQA3D and isolates failure cases of semantic-first/local-first selectors. The publishable claim is evidence-efficient selective rendering, not simply scene-graph reasoning or view selection.

## Baseline status updates
- **GraFT (2026-09-03):** promote to a first-tier near-task baseline / novelty limiter because it is training-free, directly evaluates ScanQA, and combines 3DSG symbolic geometry, BEV and task-relevant egocentric visual grounding.
- **CAPruner (ACL 2026):** still best peer-reviewed relation-pruning baseline/candidate generator; not itself a sufficient object selector.
- **PruneGround:** strong novelty limiter for language-guided spatial pruning and unnamed visual anchors, but optimized for grounding rather than open-ended QA evidence retention.
- **AgentGrounder:** strong semantic-first retrieval failure-mode baseline because its retrieval can hard-limit candidates before geometry.
- **IVSGround:** reinforces that learned query-conditioned view selection is no longer a strong main novelty; keep as view-selection baseline/secondary module.

## Top candidate this week
**SAFER-QA / QASER-CF: Constraint-first QA-specific evidence retention before selective Abstract3D rendering.**

Why #1: it is the cleanest remaining gap after GraFT/CAPruner/PruneGround/AgentGrounder. It directly targets the user's required contribution: do not render the full object set, preserve unnamed supporting evidence, avoid both semantic-TopK and proximity-only hard gates, remain training-free/lightweight, and integrate naturally before PoseAlign-T + Abstract3D.
